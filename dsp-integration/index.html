campaign Display Types & DSP Integration Proof of concept

Selling display slots to advertisers

A working proof of concept for opening Personalisation Hub inventory to advertisers through connected DSPs: a slot on a display type is offered for sale, DSPs bid for it by play window, the winning campaign is approved and handed to the existing campaign system, and the retailer sees what sold and for how much. It runs beside the platform, behind the dspIntegration flag, and changes nothing about playback.

info

This page is the front door, not the app. The POC is a real service — an API, a database, an auction job and a mock DSP exchange — so it can't run from a static page the way the other demos here do. It takes about a minute to start locally, below. If you'd rather click than clone, ask and we'll host a running instance.

Run it

# once
git clone git@github.com:offline2online/rob_ph_demos.git
cd rob_ph_demos/dsp-integration
npm install

# three terminals (or the same one, backgrounded)
npm run dev:api      # the POC API on :4000, seeded on first run
npm run dev:mocks    # stand-in DSPs on :4100
npm run dev:admin    # the admin UI on :5173

Then open http://localhost:5173. The database is seeded with three DSPs, their advertisers, example campaigns in every approval state and a booked window that has already played, so every screen has something in it. npm run db:bookings tops up the schedule with a booking for each advertiser.

What's in it

dashboardDisplay Types

Slot assignment: each slot in the rotation is owned by Headquarters, an Advertiser or the Stores.

hubDSP Integration

Exchange settings and sellers.json, advertiser settings (floor price, personalised multiplier, cost per engagement, auction schedule, allow and block lists), shared targeting variables, and a page per DSP.

sellAdvertisers / Inventory

Every advertiser across the DSPs with its approval and pricing, and the inventory they can buy — who each position is assigned to and what targeting it supports.

calendar_monthBooking schedule

Every position across its play windows — booked, available or unavailable — with booked and billed revenue per display type, and what sold by campaign type.

fact_checkCampaign Status

The campaigns advertisers and DSPs submitted, with the creative review: approve, reject with a reason, activate. A drop-in module for the platform's own Campaigns section.

gavelThe exchange

OpenRTB 2.6 DOOH bid requests to connected DSPs, a first-price auction per play window, pre-auction enforcement, hand-off to the campaign system and billing from playback data.
