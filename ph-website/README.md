**Target site and connection (read first).** PH Website work targets **personalisationhub.com** only. The one connection is the **personalisationhub.com WordPress MCP**, acting as the dedicated `ph-mcp` admin user; it is already included in the build routine. **offline2online.com is an unrelated company's site and must never be used for PH Website work**: not its Elementor MCP (`offline2online-elementor` in `.mcp.json`), not its pages. The Calendly demo link (`rob-offline2online`) is just a booking URL; it is not a reason to connect to offline2online.com. Before calling a ticket unbuildable for lack of site access, check for and use the personalisationhub.com WordPress MCP; flag it blocked only if that MCP is genuinely unavailable, and say exactly that.

## How a deploy works

After Deploy to Main, the PH Website session publishes, through the personalisationhub.com WordPress MCP as the dedicated `ph-mcp` WordPress user (not a personal account), the changed snippets from `main` (`angie-*` snippet tools). Never offline2online.com:

1. Snapshot the live snippet files before.
2. Publish the changed files.
3. Snapshot after and compare with `MANIFEST.json`.
4. Roll back by republishing the previous version.

Spec: project document "Agent endpoint release: design and build guide" (PH Website project), sections 1 and 2.

## Leak tests

`php ph-website/tests/leak.php` seeds a draft, scheduled, private, password-protected and noindex page, demo pages outside the allow-list, an out-of-range help article and internal fields (`ph_help_*`, hash, programme, project), then checks llms.txt, markdown twins, JSON-LD, the `ph-agent/v1` tools list and every tool call, the WebMCP loader and the Support Centre's public routes. `node backlog-tracker/test/help-leak.test.js` does the same for `/help-api/search`, `/help-api/article` and the remote MCP server (stubbed fetch). Both run without network inside the console's `npm run test:offline` (via `test:mcp`), so every train runs them and a leak blocks the deploy; a failure names the endpoint.

## Security gate and the production check

`SECURITY-GATE.md` is the go-live record for the agent endpoint release: the pen test checklist and results for every public endpoint, the findings (PT-01 to PT-08) and the fix for each, the leak, rate-limit, alert and RevOps results, and the post-deploy steps. `node ph-website/tests/e2e-live.mjs` is the check the PH Website session runs against production after the WordPress deploy (every page type, every tool, the twins, JSON-LD, llms.txt, the CTA links, 429 behaviour, headers and console errors; prints a pass/fail table; `--dry-run` lists the checks without network, `--stress` also exercises the WordPress route's 429). The dry run is part of `test:mcp`.

`snippets/MANIFEST.json` describes what is live. The security fixes change `ph-agent-endpoint/` (1.3.0) and `ph-blog/main.php`; regenerate the manifest entries for those files after the deploy snapshot, not before.

## Business model calculator: agent discoverability (5 Nov 2026)

One list drives everything: `calculators()` in `ph-industry-enhancements/calculators.php` (today Telco Retail, Pharmacy and Pubs & Hospitality). An entry whose slug differs from its page key names the page in `page` (`pubs` lives on the `hospitality` page; `calc_slug_for_page()` resolves it for the JSON-LD and the WebMCP config). Each entry has name, path, title, summary, outcome, fields, and optional `calc`, `clean` and `download`; it is filterable with `ph_calculators`. Adding an entry makes the industry appear in all four places with no other code change (`tests/calculators.test.php` adds a test industry and checks each):

1. **MCP** (remote server and `ph-agent/v1`): tool `calculate_business_model` (PH Agent Endpoint 1.6.0). No arguments lists the calculators and their inputs; `industry` + `inputs` returns the estimate, the figures used (and which are defaults) and a calculator link with the figures pre-filled (`?stores=120&arpu=60`). `help-search.js` allow-lists the tool name.
2. **WebMCP**: the loader registers `calculate_business_model` on every page; on an industry page with a calculator, `calc-webmcp.js` (new script version 1.9.0, config printed as `window.PH_CALCULATOR`) also registers `run_business_model_calculator`, which fills the page's own inputs, reads the estimate and, when the person's name, company, work email and `consent: true` are passed, submits the page's own download form and returns the link. It also applies `?stores=...` deep links on load. Test: `node ph-website/tests/calc-webmcp.test.mjs` (Chromium).
3. **llms.txt**: a `## Business model calculator` section (title, URL, summary, supported industries, how an agent uses it) inserted before "Pricing and trial" by `calculators-wp.php` on `ph_llms_txt` (priority 25).
4. **schema.org**: a `WebApplication` JSON-LD node (`#business-model-calculator`, inputs and output in `description` and `featureList`, `BusinessAudience`, free offer, provider `#organization`, `isPartOf` the page's `#webpage`) printed in `wp_head` on that industry's page.

**Decision, not a gap:** the .xlsx download stays gated on the person's own name, company, work email and consent (the existing lead gate). The MCP tool therefore returns the estimate and a pre-filled link and never takes or stores contact details (they would sit in a cached GET URL and logs); the on-page WebMCP tool submits the gate only when the person has supplied them and agreed. Dropping the gate for agents would be a business decision.

**Not in the repo, for the PH Website deploy session:** deploy Industries (new files `calculators.php`, `calculators-wp.php`, `calc-webmcp.js`; `main.php` requires the glue) and PH Agent Endpoint (`tools.php`), then run `e2e-live.mjs` (checks the tool, llms.txt) and the Rich Results Test on `/industries/telco/`. `MANIFEST.json` is regenerated after the deploy snapshot.
