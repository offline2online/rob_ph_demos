# Insights service foundation

The back end of Retail Media Insights & Analytics Dashboards: a read-only service at `/insights/v1/retail-media/...` with daily pre-aggregates, a shared page-filter layer and one unit-tested calculation library. The functional spec is [`README.md`](README.md); buildable requirements are in [`REQUIREMENTS.md`](REQUIREMENTS.md). The Retail Media Performance tab (front end) is built by separate tickets.

## Layout
- `src/calc/` — the calculation library (REQUIREMENTS §3.2): VAC-d assumed views, CPM / effective CPM, per slot per day, operating hours, fill, missed revenue, PG pacing, maturity, rounding, USD, standard orderings.
- `src/filters.js` — page filters `dateFrom`, `dateTo`, `storeIds[]`, `displayTypeIds[]`, `advertiserIds[]` (range capped at 366 days, years 2000–2100).
- `src/auth.js`, `src/scope.js`, `src/mint-token.js` — token resolver, server-side advertiser scoping and a dev token minter.
- `src/aggregate.js` — builds the daily aggregates from raw billing line items and slot records: delivery (display type × store × deal × DSP × advertiser) and inventory (display type × store).
- `src/display-types.js` — display type facts shared by the display endpoints: connected displays, loop from the slot configuration, VAC-d averages, hover card, shopper-journey (IAB zone) order.
- `src/store.js` — date-indexed in-memory aggregate store with a store-less daily rollup, a per-store partition and precomputed delivery cells (see **Performance and concurrency** below).
- `src/cache.js` — the bounded response cache (LRU) the HTTP server puts in front of every route.
- `src/routes/` — one file per endpoint, auto-discovered by `src/server.js`. Today: `datasets`, `dataset`, `health`, `summary`, `revenue`, `yield`, `display-types`, `slot-value`, `slot-allocation`, `missed-revenue`, `deals`, `advertisers`, `maturity` (ladder, scheduling, share by level over time, variables in use, advertiser table; `granularity`, `level`, `variable`, `scheduling`, `kind` params; `overTime` covers the whole history from the first campaign to the last played day whatever the date range, with the store, display type and advertiser filters still applying), `my-summary`.
- `src/query.js`, `src/datasets.js`, `src/mcp.js` — the export layer: every route, dataset and MCP tool call goes through `runRoute`; QuickSight datasets and MCP tools (see **QuickSight datasets and MCP tools**).
- `src/testdata.js` — deterministic 5-store test retailer (Window Portrait, Endcap Shelf-edge, Queue Screen, Dispensary Screen). Its data follows its own configuration: plays per hour = connected displays × advertiser slots × loops per hour; one sold slot-day delivers the type's average assumed views per slot per day; an advertiser slot position is sold only by the deal that assigns it (else the open auction), to that deal's buyers on their own DSP seat; auctions clear above their floor; PG and Preferred deals have one buyer; deal IDs are a per-DSP map on the catalog deal.
- `bench/dataset.js`, `bench/bench.js` — the network-scale dataset (90 days over ~865k aggregate rows, 60 stores, 4 display types, a 250-deal Programmatic guaranteed catalog) and the handler timings on it: every endpoint's p95 with the cache off, failing at 250 ms or more.
- `scripts/loadtest.js` — concurrent users against the real HTTP server (see **Performance and concurrency**).

## Run
```
npm test         # calculation, reconciliation and server tests (node:test, no dependencies)
npm run bench    # handler p95 for every endpoint on a 90-day query, cache off; fails at 250 ms
npm run loadtest # 1, 5, 10 and 20 concurrent users, warm and cold; fails if a target below is missed
npm start        # serves the test retailer on :8080 (PORT to change)
```
`GET /insights/v1/retail-media/health` → `{"status":"ok"}`. Only GET is served (405 otherwise); a malformed filter returns 400.

## Decisions and limits
- DSP Integration and PH Core are read **via their APIs behind a source adapter**, not their data stores directly. The adapter is a follow-up; today the service runs on generated test data.
- Unsold inventory ignores the advertiser filter (slot records belong to no advertiser — README open question 1 default).
- Authentication fails closed (see **Authentication and scoping** below). The real identity provider is a follow-up; until then a stand-in HMAC token resolver (`src/auth.js`) serves the test retailer.
- Slots outside a display type's operating hours are classified `outsideHours` and are never unsold; specific opening times are never returned. Operating hours default from the zone (`calc.operatingWindow`): an explicit `is24Hour` wins, an Exterior type with no flag runs 24 hours, everything else follows store opening hours, and a store with **no opening hours on record fails closed** (its in-store types have no inventory) instead of becoming 24 hours.
- **Revenue means earned (settled) revenue** wherever a table or hover says Revenue (`advertisers`, `deals`, `maturity` table, `slot-value`), to the cent. Estimated revenue appears only where labelled (`summary`, `revenue`). The advertiser view's `spend` stays billed (earned + not yet settled), so it equals the advertisers table's revenue for a range that is fully settled.
- **Hardening limits** (security and stability review, 17 Oct 2026). Tests: `test/security.test.js`.
  - *Request targets*: only origin-form targets (one leading `/` then a character that is not `/` or `\`) are served; `//x/...`, `/\`, absolute-form and `*` are **400**. The URL is parsed inside a try, the whole request listener is wrapped so no exception escapes it, and `clientError` answers 400 and destroys the socket. Only the CLI entry point adds `process.on('uncaughtException')` (log, exit 1, so a supervisor restarts it).
  - *Authenticate before routing*: an unauthenticated caller gets **401** for every path except `/health`, never 404 versus 401.
  - *Response headers*: every response carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`; CSV also has `Content-Disposition: attachment; filename="<dataset>.csv"`.
  - *MCP*: a JSON-RPC `id` is a string of at most 200 characters, a finite number or null, else **-32600** with id null. A batch holds 1 to 5 messages (MCP 2025-06-18 dropped batching). The serialised response of one HTTP request is capped at 8 MB (the text and `structuredContent` copies both count, shared across a batch): a call that would exceed it returns a tool error asking for a narrower range. Request bodies over 64 KB are **413**. The `Origin` header on `/mcp` must be in `RMI_ALLOWED_ORIGINS` (comma separated, empty by default, so any browser Origin is **403**); requests with no Origin (agents, servers) are unaffected. The `end` handler cannot exit the process: any throw answers 500.
  - *MCP arguments* are checked with `Object.hasOwn`, and `retail_media_dataset` accepts only `name`, the page filters and the extra arguments of the route that dataset is built from.
  - *Other buyers*: `winningCpm` needs at least `MIN_OTHER_BUYERS_FOR_WINNING_CPM` (2) other winning buyers. With exactly one other buyer (1 up to, not including, that number), `allPlays`, `sharePercent` and `share.allPlays` / `share.percent` are also omitted, because all plays minus the advertiser's own would be that buyer's plays. With no other buyer the advertiser has the block to itself and the share (100%) stays.
  - *Tokens*: signature must be exactly 43 base64url characters and the body base64url of at most 2048 characters; a token whose `exp` is more than 24 hours away (`MAX_TTL_SECONDS`) is refused, and `mintToken` refuses a longer `ttlSeconds`.
  - *PG pacing* (`/delivery`, `/deals`) does not scan a Programmatic guaranteed deal whose flight ended before `dateFrom` or starts after `dateTo`, so cost follows the requested range, not history. For a flight that ended before the range, `/deals` `pacing.delivered` and `pacing.percent` are `null` (the rest of the pacing facts are still returned).
  - *Slow connections*: `headersTimeout` 10 s, `requestTimeout` 30 s, `keepAliveTimeout` 5 s, `maxConnections` 1000 (env `RMI_HEADERS_TIMEOUT_MS`, `RMI_REQUEST_TIMEOUT_MS`, `RMI_KEEPALIVE_TIMEOUT_MS`, `RMI_MAX_CONNECTIONS`); expiry is checked every second.

## Performance and concurrency
REQUIREMENTS §3.4 (p95 under 2 s per endpoint for a 90-day range) has to hold with several people using the service at once, not just one. At network scale (864k aggregate rows) a request used to cost 30–800 ms of CPU on the one thread, so concurrent users queued behind each other and `/health` waited seconds behind them. Responses did not change: `test/equivalence.test.js` compares every endpoint against the straight scan, and the cache is tested for byte-for-byte equality with an uncached handler.
- **No full scans.** Built once at load, beside the fine cube (date × display type × store × deal × DSP × advertiser): a **store-less daily rollup** (date × display type × deal × DSP × advertiser) that every query without a store filter reads; a **per-store partition** of the fine cube (positions into it, in its order), so a store filter reads only those stores' rows; a **per-advertiser partition** of the rollup (an advertiser's own rows); inventory gets the rollup and the store partition too. Advertiser Delivery also reads **precomputed cells** (date × display type × deal, or the open auction: plays, revenue, views, the cleared CPM of each winning buyer and which advertisers won plays), because what it shows about other buyers is a function of those cells alone. A cell's `cpms` list holds one cleared CPM (revenue ÷ views) per winning buyer, because the winning CPM percentiles are order statistics over buyers, not sums. Rows carry integer codes (`dealIx`, `typeIx`, `advIx`, `dayIx`) so the hot handlers (`deals`, `advertisers`, `delivery`, `deals-by-display-type`, Programmatic guaranteed pacing) accumulate into dense arrays instead of building a string key per row. `new AggregateStore(data, { indexed: false })` keeps the straight scan as the reference implementation.
- **Exactness.** Everything is summed in the same order as before except where stores are merged: a rollup adds the stores of a day first, so a sum can differ from the straight scan in its last binary digit. Money and percentages are rounded to cents or whole numbers before they leave, and views and slots are whole numbers; the one unrounded figure, `/yield` `assumedViews`, is a sum of whole-number views. The equivalence test asserts deep equality on the test retailer (every endpoint × single store, two stores, each display type, each advertiser, each deal type × 7, 30, 90 and 366 days × admin and every advertiser) and on a busy open auction with a different clearing price in every store.
- **Response cache** (`src/cache.js`). An LRU of at most **500 entries and 64 MB** of serialised responses (a single response over 64 MB is not cached), in front of every authenticated route, after authentication, the `insights:read` and advertiser-access checks, and server-side scoping, so a hit can never skip a check. The key is the route; the principal (an **advertiser** is its own key space by `principalType` and `principalId`; **all admins share one**); the filters after `parseFilters` and `scopeFilters` (an advertiser's pinned `advertiserIds` and display types, never the client's), each list sorted because every handler reads them as sets; and the remaining query parameters, sorted. Errors (400, 403, 401) and the CSV form of a dataset are never cached; `/health` is not. The store is immutable after load, so an entry is valid until the store is replaced: **`server.replaceStore(next)` swaps the store and clears the cache**. Hits skip `JSON.stringify` too. Tests: `test/cache.test.js` (bounds, recency, key shape, advertiser A never receives B's or an admin's entry, nobody receives an advertiser's, byte-for-byte equality with an uncached server). `createServer({ cache: false })` turns it off; `server.cache` exposes `hits`, `misses`, `size`, `bytes`. The first user after a start or rebuild pays for one cold page (about 0.25–0.35 s of handler time for the retailer page's 11 endpoints at bench scale); everyone after that is served from memory.
- **The event loop stays responsive.** Handlers are synchronous, so the server runs **one per event-loop turn** from a FIFO queue: any I/O (a `/health` probe, a new connection) is serviced between two handlers instead of behind every request that arrived first. `/health` is not queued. A queue longer than `maxQueue` (env `RMI_MAX_QUEUE`, default 512) answers **503 with `Retry-After: 1`**. At bench scale with the cache off every handler's p95 is under 250 ms (`npm run bench` fails otherwise; the slowest is advertiser Delivery at about 100–150 ms, on an advertiser with delivery on every one of 250 deals), and under 60 ms for all the others except `deals-by-display-type` (about 65–100 ms). **Decision:** a `worker_threads` pool was not needed to get there and is not built: it would copy the 600 MB store into every worker. If handlers outgrow 250 ms at a larger scale, the pool would answer from this same queue. Tests: `test/queue.test.js`.
- **Load test** (`npm run loadtest`, `scripts/loadtest.js`). The real HTTP server with token auth, in its own process, over the bench dataset; each simulated user loads the retailer page's 11 endpoints (`summary`, `revenue`, `deals`, `slot-value`, `slot-allocation`, `missed-revenue`, `yield`, `display-types`, `advertisers`, `maturity`, `filter-options`) for 90 days, 3 times, 6 requests at a time like a browser, while a `/health` probe runs on its own thread. It prints the CPU count and, for 1, 5, 10 and 20 users, request and page p50/p95/p99, `/health` p95 and max, requests per second and the server's peak RSS, **warm** (every user asks for the same thing, cache on and already filled) and **cold** (each user its own store filter, cache off, so every request runs its handler). It exits 1 if a target is missed: 20 users warm and 10 users cold must each have request and page p95 under 2,000 ms, and `/health` p95 under 100 ms in both. `LOADTEST_USERS`, `LOADTEST_MODES` and `LOADTEST_LOADS` narrow a run.
- **Measured** (17 Oct 2026, 4 vCPU sandbox, node 22, 864k aggregate rows; the review's pre-change figures were 10.6 s request p95 at 5 users, 20.1 s at 10 and 43.9 s at 20, throughput 13 req/s):

  | Users | Warm: request p95 | page p95 | Cold: request p95 | page p95 | `/health` p95 (warm / cold) |
  |---|---|---|---|---|---|
  | 1 | 7 ms | 9 ms | 104 ms | 105 ms | 3 / 24 ms |
  | 5 | 22 ms | 24 ms | 385 ms | 454 ms | 2 / 24 ms |
  | 10 | 59 ms | 63 ms | 936 ms | 1,049 ms | 2 / 23 ms |
  | 20 | 104 ms | 109 ms | 1,664 ms | 1,677 ms | 3 / 26 ms |

  Cold throughput is about 145 requests a second (one CPU: every request runs its handler); warm is about 2,400. The rollups, partitions and cells cost memory: the server's RSS is about 600 MB at bench scale (it was 320–490 MB). Cold with more than about 10 users on one core is CPU-bound, so beyond that run more replicas rather than more threads.

## Endpoint: sales-uplift
`GET /sales-uplift?campaignId=` (advertiser-callable) — `campaigns` (the drop-down: `id`, `advertiserId`, `advertiserName`, `productName`, `sku`?, `start`, `end`; newest first; only the `advertiserIds` page filter applies, and an advertiser login is pinned to itself), `campaignId` (the one shown: the newest finished campaign with POS data and a Control stores exclusion unless one is requested; an unknown or other advertiser's id is **400**), `state` (`ok`, `no-pos`, `no-control`, `no-campaign`), `product`, `matchedOn` (`sku` | `product name`), `windows`, `campaignStores` / `controlStores` (`count`, `names`), `tierMix` (`[{tier, percent}]`, adds to 100) and, when `ok`, `tiles` (`upliftPercent`, `incrementalSales`, `spend`, `iroas`) and `series` (per day: `phase`, `campaignSales`, `controlSales`, per-store figures, `difference`, and each group's index to its 30-day pre-period mean). Until the source adapter exists the products, Transaction API sales, control segment and tier mix come from `src/uplift.js` (deterministic sample data, described at its top); `test/sales-uplift.test.js` checks the series reconcile to those transactions and the isolation rules.

## Authentication and scoping
- `createServer({ store, authenticate })` **requires** `authenticate(req)`; there is no default. It returns `{principalType: 'admin'|'advertiser', principalId, scopes}` (DSP Integration §9.5) or `null`; `null`, a malformed principal or a throw is **401**. Only `/health` (`public: true`) is open. Every other route also needs the **`insights:read`** scope: an authenticated caller without it is **403** (DSP Integration §9.5).
- Stand-in resolver: `src/auth.js` verifies `Authorization: Bearer <token>`, an HMAC-SHA256 signed, expiring token. The secret is `RMI_AUTH_SECRET` (32+ characters, no default; `npm start` refuses to run without it). Mint one with `RMI_AUTH_SECRET=… node src/mint-token.js admin retailer` or `… advertiser adv-acme`. Tokens in a query string are never read.
- **Deny by default, per route.** A route module declares who may call it: no declaration means retailer (`admin`) only and an advertiser gets **403**. To open a route to advertisers, export `advertiserAccess: true` and read data only through the `filters` the server passes in (never `params`). `public: true` skips authentication.
- Advertiser-callable: `display-types`, `filter-options` and the four advertiser view endpoints below (`delivery`, `deals-by-display-type`, `audience`, `my-targeting`), `my-summary` and `sales-response`. `summary`, `revenue`, `yield`, `deals`, `advertisers`, `slot-value`, `slot-allocation`, `maturity` (network-wide figures or other advertisers' data) and `missed-revenue` (downtime, lost revenue, offline displays) are 403 for advertisers.
- `scopeFilters(filters, principal, store)` pins an advertiser to `advertiserIds: [principalId]`, ignoring any client value, and limits `displayTypeIds` to the advertiser's allowed display types.
- `GET /filter-options` — `firstDataDay` and `lastDataDay` (the first and last **played** day; never a reservation date, so "Last n days" ends on played data), `displayTypes` `[{id, name}]` for the Display type filter: all for a retailer; for an advertiser, the display types in its deals' slot assignments plus those its campaigns target. **Decision:** a campaign with no display types contributes nothing (fail closed), unlike the store's "targets all" reading for campaign counts.
- Page filters are capped: a range over 366 days, or a year outside 2000–2100, is 400 (an unbounded `/maturity` range blocked the single-threaded server for minutes).

## Endpoints: summary, revenue, yield
All take the page filters (`dateFrom`, `dateTo`, `storeIds[]`, `displayTypeIds[]`, `advertiserIds[]`).
- `GET /summary` — `earnedRevenue` (every played day is earned), `estimatedRevenue` (Programmatic guaranteed reservations booked ahead: the 30 days after the last played day, whatever the date range, under the same store, display type and advertiser filters and the `dsps` / `dealTypes` chart filters), `estimatedWindow {dateFrom, dateTo}` (that 30 days), `effectiveCpm` (earned ÷ earned views × 1,000, to the cent; `null` with no views), `connectedDsps` (DSPs with a connected seat) and `inventorySold` `{percent, slotsSold, slotsAvailable, slotsOffline}` across all advertiser slots inside operating hours: `percent` = sold ÷ (sold + available + offline), and the three counts sum to all advertiser slots, so it equals `/missed-revenue` `total.fillPercent` for the same filters. Optional `dsps[]` / `dealTypes[]` narrow the money figures only (inventory has no DSP or deal type).
- `GET /revenue?granularity=day|week|month&aheadDays=0..120&dsps[]&dealTypes[]` — `lastDataDay` and rows `{period, dsp, dealType, earned, estimated, advertisers}` (`advertisers` = distinct advertisers with earned revenue in that period × DSP × deal type) ordered by period, DSP (DV360, The Trade Desk, Amazon DSP), then the four deal types. `aheadDays` (whole number 0–120, default 0; 400 otherwise) adds the booked-ahead periods after the last played day (`earned` 0, `estimated` > 0, `ahead: true`; a week or month that also has played days is not ahead). The page asks for 14 (Day), 42 (Week) or up to 31 Dec (Month, 81 days from 11 Oct).
- `GET /yield?dealType=` — one row per connected DSP in the standard order: `{dsp, effectiveCpm, earnedRevenue, assumedViews}` from settled billing; `effectiveCpm` is `null` when a DSP has no delivery.

Money is USD rounded to cents; `/summary` equals the sum of `/revenue` rows for the same filters to within a cent per row. An unknown `dealTypes` / `dealType` returns 400.

## Endpoints: display-types, slot-value, slot-allocation, missed-revenue
All take the page filters; rows come in shopper-journey zone order.
- Display endpoints (`display-types`, `slot-value`, `slot-allocation`, `missed-revenue`) are in shopper-journey zone order; a display type with no connected display in the filtered stores is left out. Hover-card fields that are not stored are omitted, never defaulted. Money parts are rounded first so rows add to the totals returned.
- **Connected displays (README open question 5, undecided):** a display counts if it was connected at any point in the date range (`connectedFrom` / `connectedTo` on the display; none set means always connected). Switching to "online now" is a one-line change in `connectedIn()` in `src/display-types.js`.
- Fill on `missed-revenue` and `slot-allocation` is sold ÷ (sold + unsold + offline), the same as the Inventory sold tile, so sold + unsold + offline = all advertiser slots inside operating hours.
- `slot-value` rows carry the hover's identity with fill applied, each factor in the row: `perSlotPerDay` = `effectiveCpm` × `averageAssumedViewsPerSlotPerDay` ÷ 1,000 × `advertiserSlotsSoldShare` (settled assumed views as a share of what every advertiser slot on every connected display would deliver over the range). Money totals are earned revenue to the cent.
- `missed-revenue` returns 403 to an advertiser login (downtime and lost revenue are retailer-only). Downtime lost revenue comes from the lost-revenue report values carried on offline slot records.

## Endpoints: deals, advertisers
Both take the page filters. Reference data (deals, buyers, slot assignments) comes from `store.catalog.deals`, filled by the source adapter from DSP Integration; today it is the test catalog in `src/testdata.js`.
- `GET /deals?dealType=` — one row per named deal (Open auction is not a deal) in the standard deal-type order: name, description, `dealIds` (`{dsp, dspLabel, dealId}`, one `PH-` ID per DSP that has an invited buyer, read from the catalog deal's per-DSP `dealIds` map; `dspLabel` is Google DSP (DV360) / The Trade Desk / Amazon Ads DSP), `slots` (display type, playlist · zone, IAB zone, advertiser slot n / loop slot n, plays per window), `advertisers` with their DSP (ordered DV360, The Trade Desk, Amazon DSP, then name), `fill`, `pacing` (Programmatic guaranteed only, else `null`), `revenue` (earned) and `cpm` (`kind` is `floor` for Private auction, `fixed` otherwise). An unknown `dealType` returns 400.
- The display type page filter applies to every part of a deal row: `slots` and `fill` cover only assigned slots on the filtered types, and a deal with none drops out. `fill.percent` is `null` when there is no opportunity (no cap: `fill` and Slots won are honest numbers).
- PG `pacing` is **deal-wide**: delivered is settled VAC-d (`earnedViews`) from the flight start to `dateTo`, and the store and display type filters are ignored so the guarantee and delivered cover the same scope (`scope: 'deal'`). One pass over the delivery rows, grouped by deal, serves every PG deal. It is as at `dateTo`: before the flight `startsInDays` is set and `percent` is `null`; during it `daysElapsed` / `daysRemaining` count from the flight start; after it `daysRemaining` is 0, `flightEnded` is true and `guaranteedToDate` equals the whole-flight guarantee. `guaranteedToDate` = forecast × (1 − buffer) × days elapsed / flight days.
- `GET /advertisers` — `top` (10 by revenue) and `all`: earned revenue, `share` (of earned revenue, whole numbers adding to 100), `dealsOn` (names and types), `slotsCovered`, `slotsWonPercent` (`null` with no opportunity; `slotsWonCount` / `slotsOpportunity` give the counts), `effectiveCpm` (settled billing) and `dsp`. `slotsWon.complete` is false when the range is longer than the 90-day settled-bid retention (README open question 3).
- **Decision:** slot records carry no position, so a display type's sold + unsold slots inside operating hours are split equally across its advertiser positions. Opportunities are sold + unsold + offline (matching `calc.fillPercent`). Deal `fill` = slots won on the deal ÷ the opportunities of its assigned slots; `slotsWonPercent` is the same for an advertiser's covered slots, counting only the advertiser's own wins on its deals' positions (not wins on those display types from other deals or the open auction), and only covered slots on the filtered display types.
- An advertiser login sees only the deals it is invited to, with only its own buyer and the deal ID for its own DSP, and only its own advertiser row.

## Endpoints: advertiser view
`delivery`, `deals-by-display-type`, `audience`, `my-summary` and `my-targeting` are declared `advertiserAccess: true`. They are per advertiser: an advertiser login is pinned to its own id by `scopeFilters`; a retailer user must pass exactly one `advertiserIds` value (400 otherwise). They never return another advertiser's id, name, plays or CPM, and no downtime, offline or lost-revenue field.
- `GET /delivery?dealId=` — `totals` and `days[]` (every day in the range): `playsWon`, `spend`, `vsPreviousDay` (`change`, and whole-number `percent` unless the previous day was 0; the first day compares with the day before `dateFrom`) and `deals[]`, one block per deal in scope (the deals the advertiser buys or has delivery on) then the open auction, in that order. Private auction and Open auction blocks: `playsWon`, `allPlays` (all buyers), `sharePercent`, `yourCpm` (omitted with no plays won), `winningCpm {p25, median, p75}` and `floorCpm {min, max}` (the deal floor, or the range of the floors of the display types its campaigns run on). Programmatic guaranteed and Preferred deal blocks: `playsWon`, `fixedCpm`, `otherBuyers: "None"`. `dealId` is a deal id or `open-auction` and narrows the lines and the blocks; an id that is not one of `dealOptions` is 400. `pacing[]` (Programmatic guaranteed only): the flight and a `series` of `guaranteed` against `delivered` VAC-d, the advertiser's own delivery cumulative from the flight start.
- **Winning CPM** is shown only when at least `MIN_OTHER_BUYERS_FOR_WINNING_CPM` (2, `src/constants.js`, README open question 4) other buyers won plays on that block that day; otherwise the field is omitted. `p25`, `median` and `p75` are the 25th percentile, median and 75th percentile (linear interpolation, to the cent) of the cleared CPMs of the winning buyers on the block that day (one CPM per buyer and display type, from billing line items: revenue ÷ VAC-d), the advertiser included. `GET /deals-by-display-type` returns the same `winningCpm` on Private auction deal rows, on a new Open auction row (`id: "open-auction"`, listed last under each display type the advertiser's campaigns run on, outside the group's own totals) and on each display type group, pooled over its auction rows; never on Programmatic guaranteed or Preferred deal rows. No highest value and no per-buyer CPM leaves the service. Buyers are only counted, never named. The service returns cleared CPMs as the source has them: it never clamps to the floor.
- `GET /deals-by-display-type` — `groups[]` in shopper-journey order, one per display type the advertiser's deals are assigned to or delivered on, each with the display type hover card, `dealCount`, `slots`, `playsWon`, `assumedViews`, `spend`, `effectiveCpm`, `sharePercent` (share of the advertiser's deal spend; whole numbers adding to 100) and `deals[]`: `name`, `description`, the advertiser's own DSP `dealIds`, assigned `slots`, `playsWon`, `assumedViews`, `spend`, `effectiveCpm` and `share {playsWon, allPlays, percent, advertisersOnDeal}` (a count, never names). Open auction plays are not on a deal and are not included. `slotsWon.complete` is false beyond the 90-day settled-bid retention.
- `GET /audience` — `assumedViews` (VAC-d delivered) and a daily `trend`.
- `GET /my-summary` — the advertiser's `spend` and `playsWon` (equal to `/delivery`'s `totals` for the same filters) and `dealsOn`, the number of deals it is a buyer on that are live in the range (a deal with a flight is live when the flight overlaps the range; Open auction is not a deal). Advertiser-callable and scoped server-side like `/delivery`; a retailer passes exactly one `advertiserIds`.
- `GET /sales-response` — Sales response after personalised plays (advertiser-callable, so also in a retailer's maturity section). Page filters plus `campaignId` (must be one of the listed campaigns, else 400), `window` (1–120 whole minutes, default 10), `step` (1, 5 or 15, not larger than the window), `view` (`step` | `running`) and `hourFrom`/`hourTo` (a band inside the operating hours, else 400). Returns `campaigns` (only those with personalised variants; an advertiser login gets no advertiser id, name or DSP), `lines` (`personalised`, `localised`, `control`; each `points[{from,to,label,value,sales,plays,shoppers}]`, `value` = sales ÷ shoppers × 1,000; `control` has `available:false` and a `note` when the campaign has no Control stores), `hours`, `coverage` and `emptyReason`/`emptyText` (`no-pos`, `no-campaigns`, `no-personalised-plays`). Needs `catalog.transactionApi` and `catalog.controlStores`.
- `GET /my-targeting` — `level` (omitted when no campaign is live in the range), `variablesUsed`, `scheduling {uses, scheduledCampaigns, campaigns, schedules}`, `otherVariablesAvailable {Localised, Personalised}` (Shared Targeting Variables shared with the advertiser's DSP that its campaigns do not use; `catalog.sharedVariables[dsp]`, defaulting to all Localisation and no Personalisation) and `usesEverySharedVariable`.
- **Reconciliation:** parts are rounded first and totals are their sums (money to the cent per day or per deal row, plays and views as whole numbers), so days, rows and groups add to the totals returned, and the totals equal the advertiser's billing for the same filters to within a cent per rounded part. `spend` and `effectiveCpm` use all billing (settled and not yet settled), so spend ÷ assumed views × 1,000 equals the CPM shown beside it.
- **Limit:** because totals follow the page filters, an advertiser who narrows `storeIds` could difference two responses to estimate one other buyer's plays. Closing that needs a minimum-cohort rule on the filtered views, which the decision on README open question 4 does not cover.

## QuickSight datasets and MCP tools
REQUIREMENTS §2 and §7 step 4: the same API, exposed two more ways. **No on-page CTA links to either.** Both are thin: a dataset or a tool call runs the endpoint's own handler through `runRoute` (`src/query.js`), the same function the HTTP routes use, so the role check, page filters, server-side advertiser scoping and rounding are the API's, not a copy that could drift.
- **QuickSight datasets.** `GET /datasets` lists the datasets the caller may read; `GET /dataset?name=<dataset>&format=json|csv` returns one as `{name, description, grain, columns:[{name,type}], rows}` (`type` is STRING, INTEGER, DECIMAL, DATE or BOOLEAN) or as CSV with a header row. All page filters and the endpoint's own parameters (`granularity`, `dealType`, `dealId`, ...) pass through. Rows are flat: nested objects become `a_b` columns, lists become `"; "`-joined text, and CSV cells that start with `= + - @` are neutralised. Retailer datasets: `summary`, `revenue`, `yield`, `display-types`, `slot-value`, `slot-allocation`, `missed-revenue`, `deals`, `advertisers`, `maturity-ladder`, `maturity-advertisers`, `maturity-variables`. Advertiser datasets: `delivery`, `delivery-deals`, `deals-by-display-type`, `audience`, `my-summary`, `my-targeting` (plus `display-types`). A dataset is advertiser-readable exactly when its endpoint is; an advertiser asking for any other is 403, and its `advertiserIds` is pinned to itself. Point QuickSight at the CSV or JSON URL with a bearer token (a QuickSight data source that cannot send one needs the gateway in front of this service to add it); QuickSight needs a stable schema, so an empty range returns `columns: []`.
- **MCP tools.** `POST /insights/v1/retail-media/mcp` is a JSON-RPC 2.0 MCP endpoint (`initialize`, `ping`, `tools/list`, `tools/call`; batches accepted; 64 KB body cap). One read-only tool per endpoint (`retail_media_summary`, `retail_media_revenue`, `retail_media_yield`, `retail_media_display_types`, `retail_media_slot_value`, `retail_media_slot_allocation`, `retail_media_missed_revenue`, `retail_media_deals`, `retail_media_advertisers`, `retail_media_maturity`, `retail_media_delivery`, `retail_media_deals_by_display_type`, `retail_media_audience`, `retail_media_my_summary`, `retail_media_my_targeting`) plus `retail_media_dataset` (no name lists the datasets). Arguments are the page filters plus the endpoint's own; an unknown argument is a tool error. Results are the endpoint's JSON as `structuredContent` and as text. Same bearer-token authentication as every route (401 otherwise); `tools/list` shows an advertiser only the tools it may call, and calling any other returns an `isError` result.
- **Decision (to confirm):** MCP is a plain JSON-RPC POST endpoint rather than an SDK server, because this service has no dependencies; the "MCP plumbing" owned by PH Core (REQUIREMENTS §6) may front it or replace the transport without changing the tools.
- Tests: `test/export.test.js` (datasets equal the endpoints, CSV, advertiser isolation and spoofing, MCP protocol, tool results equal the endpoints, bad arguments).

`/advertisers` rows also carry `iroas` (`value` = measured incremental sales ÷ measured spend to 2 dp, `null` when no campaign was measured; `incrementalSales`, `measuredSpend`, `measuredCampaigns`, `totalCampaigns`, `notMeasured[]` / `flagged[]` of `{campaignId, product, reason}`, `campaignStores`, `controlStores`, `dateFrom`, `dateTo`), computed with the Sales uplift calculation over campaigns whose flight overlaps the applied range and filters; the response has `posData` (false when no campaign in range had POS sales). Retailer only: `/advertisers` is not advertiser-callable.
