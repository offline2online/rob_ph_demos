# Insights service foundation

The back end of Retail Media Insights & Analytics Dashboards: a read-only service at `/insights/v1/retail-media/...` with daily pre-aggregates, a shared page-filter layer and one unit-tested calculation library. The functional spec is [`README.md`](README.md); buildable requirements are in [`REQUIREMENTS.md`](REQUIREMENTS.md). The Retail Media Performance tab (front end) is built by separate tickets.

## Layout
- `src/calc/` — the calculation library (REQUIREMENTS §3.2): VAC-d assumed views, CPM / effective CPM, per slot per day, operating hours, fill, missed revenue, PG pacing, maturity, rounding, USD, standard orderings.
- `src/filters.js` — page filters `dateFrom`, `dateTo`, `storeIds[]`, `displayTypeIds[]`, `advertiserIds[]` (range capped at 366 days, years 2000–2100).
- `src/auth.js`, `src/scope.js`, `src/mint-token.js` — token resolver, server-side advertiser scoping and a dev token minter.
- `src/aggregate.js` — builds the daily aggregates from raw billing line items and slot records: delivery (display type × store × deal × DSP × advertiser) and inventory (display type × store).
- `src/display-types.js` — display type facts shared by the display endpoints: connected displays, loop from the slot configuration, VAC-d averages, hover card, shopper-journey (IAB zone) order.
- `src/store.js` — date-indexed in-memory aggregate store.
- `src/routes/` — one file per endpoint, auto-discovered by `src/server.js`. Today: `datasets`, `dataset`, `health`, `summary`, `revenue`, `yield`, `display-types`, `slot-value`, `slot-allocation`, `missed-revenue`, `deals`, `advertisers`, `maturity` (ladder, scheduling, share by level over time, variables in use, advertiser table; `granularity`, `level`, `variable`, `scheduling`, `kind` params).
- `src/query.js`, `src/datasets.js`, `src/mcp.js` — the export layer: every route, dataset and MCP tool call goes through `runRoute`; QuickSight datasets and MCP tools (see **QuickSight datasets and MCP tools**).
- `src/testdata.js` — deterministic 5-store test retailer (Window Portrait, Endcap Shelf-edge, Queue Screen, Dispensary Screen). Its data follows its own configuration: plays per hour = connected displays × advertiser slots × loops per hour; one sold slot-day delivers the type's average assumed views per slot per day; an advertiser slot position is sold only by the deal that assigns it (else the open auction), to that deal's buyers on their own DSP seat; auctions clear above their floor; PG and Preferred deals have one buyer; deal IDs are a per-DSP map on the catalog deal.
- `bench/bench.js` — 90-day query over ~865k aggregate rows with a 250-deal Programmatic guaranteed catalog; times every endpoint and fails if any p95 is 2000 ms or more.

## Run
```
npm test         # calculation, reconciliation and server tests (node:test, no dependencies)
npm run bench    # p95 for every endpoint on a 90-day query; fails at 2000 ms
npm start        # serves the test retailer on :8080 (PORT to change)
```
`GET /insights/v1/retail-media/health` → `{"status":"ok"}`. Only GET is served (405 otherwise); a malformed filter returns 400.

## Decisions and limits
- DSP Integration and PH Core are read **via their APIs behind a source adapter**, not their data stores directly. The adapter is a follow-up; today the service runs on generated test data.
- Unsold inventory ignores the advertiser filter (slot records belong to no advertiser — README open question 1 default).
- Authentication fails closed (see **Authentication and scoping** below). The real identity provider is a follow-up; until then a stand-in HMAC token resolver (`src/auth.js`) serves the test retailer.
- Slots outside a display type's operating hours are classified `outsideHours` and are never unsold; specific opening times are never returned. Operating hours default from the zone (`calc.operatingWindow`): an explicit `is24Hour` wins, an Exterior type with no flag runs 24 hours, everything else follows store opening hours, and a store with **no opening hours on record fails closed** (its in-store types have no inventory) instead of becoming 24 hours.
- **Revenue means earned (settled) revenue** wherever a table or hover says Revenue (`advertisers`, `deals`, `maturity` table, `slot-value`), to the cent. Estimated revenue appears only where labelled (`summary`, `revenue`). The advertiser view's `spend` stays billed (earned + not yet settled), so it equals the advertisers table's revenue for a range that is fully settled.
- **Hardening limits** (security and stability review, 17 Oct 2026). Tests: `test/security.test.js`.
  - *Request targets*: only origin-form targets (one leading `/` then a character that is not `/` or `\`) are served; `//x/...`, `/\`, absolute-form and `*` are **400**. The URL is parsed inside a try, the whole request listener is wrapped so no exception escapes it, and `clientError` answers 400 and destroys the socket. Only the CLI entry point adds `process.on('uncaughtException')` (log, exit 1, so a supervisor restarts it).
  - *Authenticate before routing*: an unauthenticated caller gets **401** for every path except `/health`, never 404 versus 401.
  - *Response headers*: every response carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`; CSV also has `Content-Disposition: attachment; filename="<dataset>.csv"`.
  - *MCP*: a JSON-RPC `id` is a string of at most 200 characters, a finite number or null, else **-32600** with id null. A batch holds 1 to 5 messages (MCP 2025-06-18 dropped batching). The serialised response of one HTTP request is capped at 8 MB (the text and `structuredContent` copies both count, shared across a batch): a call that would exceed it returns a tool error asking for a narrower range. Request bodies over 64 KB are **413**. The `Origin` header on `/mcp` must be in `RMI_ALLOWED_ORIGINS` (comma separated, empty by default, so any browser Origin is **403**); requests with no Origin (agents, servers) are unaffected. The `end` handler cannot exit the process: any throw answers 500.
  - *MCP arguments* are checked with `Object.hasOwn`, and `retail_media_dataset` accepts only `name`, the page filters and the extra arguments of the route that dataset is built from.
  - *Other buyers*: `winningCpm` needs at least `MIN_OTHER_BUYERS_FOR_WINNING_CPM` (2) other winning buyers. With exactly one other buyer (1 up to, not including, that number), `allPlays`, `sharePercent` and `share.allPlays` / `share.percent` are also omitted, because all plays minus the advertiser's own would be that buyer's plays. With no other buyer the advertiser has the block to itself and the share (100%) stays.
  - *Tokens*: signature must be exactly 43 base64url characters and the body base64url of at most 2048 characters; a token whose `exp` is more than 24 hours away (`MAX_TTL_SECONDS`) is refused, and `mintToken` refuses a longer `ttlSeconds`.
  - *PG pacing* (`/delivery`, `/deals`) does not scan a Programmatic guaranteed deal whose flight ended before `dateFrom` or starts after `dateTo`, so cost follows the requested range, not history. For a flight that ended before the range, `/deals` `pacing.delivered` and `pacing.percent` are `null` (the rest of the pacing facts are still returned).
  - *Slow connections*: `headersTimeout` 10 s, `requestTimeout` 30 s, `keepAliveTimeout` 5 s, `maxConnections` 1000 (env `RMI_HEADERS_TIMEOUT_MS`, `RMI_REQUEST_TIMEOUT_MS`, `RMI_KEEPALIVE_TIMEOUT_MS`, `RMI_MAX_CONNECTIONS`); expiry is checked every second.

## Authentication and scoping
- `createServer({ store, authenticate })` **requires** `authenticate(req)`; there is no default. It returns `{principalType: 'admin'|'advertiser', principalId, scopes}` (DSP Integration §9.5) or `null`; `null`, a malformed principal or a throw is **401**. Only `/health` (`public: true`) is open. Every other route also needs the **`insights:read`** scope: an authenticated caller without it is **403** (DSP Integration §9.5).
- Stand-in resolver: `src/auth.js` verifies `Authorization: Bearer <token>`, an HMAC-SHA256 signed, expiring token. The secret is `RMI_AUTH_SECRET` (32+ characters, no default; `npm start` refuses to run without it). Mint one with `RMI_AUTH_SECRET=… node src/mint-token.js admin retailer` or `… advertiser adv-acme`. Tokens in a query string are never read.
- **Deny by default, per route.** A route module declares who may call it: no declaration means retailer (`admin`) only and an advertiser gets **403**. To open a route to advertisers, export `advertiserAccess: true` and read data only through the `filters` the server passes in (never `params`). `public: true` skips authentication.
- Advertiser-callable: `display-types`, `filter-options` and the four advertiser view endpoints below (`delivery`, `deals-by-display-type`, `audience`, `my-targeting`). `summary`, `revenue`, `yield`, `deals`, `advertisers`, `slot-value`, `slot-allocation`, `maturity` (network-wide figures or other advertisers' data) and `missed-revenue` (downtime, lost revenue, offline displays) are 403 for advertisers.
- `scopeFilters(filters, principal, store)` pins an advertiser to `advertiserIds: [principalId]`, ignoring any client value, and limits `displayTypeIds` to the advertiser's allowed display types.
- `GET /filter-options` — `displayTypes` `[{id, name}]` for the Display type filter: all for a retailer; for an advertiser, the display types in its deals' slot assignments plus those its campaigns target. **Decision:** a campaign with no display types contributes nothing (fail closed), unlike the store's "targets all" reading for campaign counts.
- Page filters are capped: a range over 366 days, or a year outside 2000–2100, is 400 (an unbounded `/maturity` range blocked the single-threaded server for minutes).

## Endpoints: summary, revenue, yield
All take the page filters (`dateFrom`, `dateTo`, `storeIds[]`, `displayTypeIds[]`, `advertiserIds[]`).
- `GET /summary` — `earnedRevenue`, `estimatedRevenue` (booked-ahead, not yet played) and `inventorySold` `{percent, slotsSold, slotsAvailable, slotsOffline}` across all advertiser slots inside operating hours: `percent` = sold ÷ (sold + available + offline), and the three counts sum to all advertiser slots, so it equals `/missed-revenue` `total.fillPercent` for the same filters. Optional `dsps[]` / `dealTypes[]` narrow the money figures only (inventory has no DSP or deal type).
- `GET /revenue?granularity=day|week|month&dsps[]&dealTypes[]` — rows `{period, dsp, dealType, earned, estimated}` ordered by period, DSP (DV360, The Trade Desk, Amazon DSP), then the four deal types.
- `GET /yield?dealType=` — one row per connected DSP in the standard order: `{dsp, effectiveCpm, earnedRevenue, assumedViews}` from settled billing; `effectiveCpm` is `null` when a DSP has no delivery.

Money is USD rounded to cents; `/summary` equals the sum of `/revenue` rows for the same filters to within a cent per row. An unknown `dealTypes` / `dealType` returns 400.

## Endpoints: display-types, slot-value, slot-allocation, missed-revenue
All take the page filters; rows come in shopper-journey zone order.
- Display endpoints (`display-types`, `slot-value`, `slot-allocation`, `missed-revenue`) are in shopper-journey zone order; a display type with no connected display in the filtered stores is left out. Hover-card fields that are not stored are omitted, never defaulted. Money parts are rounded first so rows add to the totals returned.
- **Connected displays (README open question 5, undecided):** a display counts if it was connected at any point in the date range (`connectedFrom` / `connectedTo` on the display; none set means always connected). Switching to "online now" is a one-line change in `connectedIn()` in `src/display-types.js`.
- Fill on `missed-revenue` and `slot-allocation` is sold ÷ (sold + unsold + offline), the same as the Inventory sold tile, so sold + unsold + offline = all advertiser slots inside operating hours.
- `slot-value` rows carry the hover's identity with fill applied, each factor in the row: `perSlotPerDay` = `effectiveCpm` × `averageAssumedViewsPerSlotPerDay` ÷ 1,000 × `advertiserSlotsSoldShare` (settled assumed views as a share of what every advertiser slot on every connected display would deliver over the range). Money totals are earned revenue to the cent.
- `missed-revenue` returns 403 to an advertiser login (downtime and lost revenue are retailer-only). Downtime lost revenue comes from the lost-revenue report values carried on offline slot records.

## Endpoints: deals, advertisers
Both take the page filters. Reference data (deals, buyers, slot assignments) comes from `store.catalog.deals`, filled by the source adapter from DSP Integration; today it is the test catalog in `src/testdata.js`.
- `GET /deals?dealType=` — one row per named deal (Open auction is not a deal) in the standard deal-type order: name, description, `dealIds` (`{dsp, dspLabel, dealId}`, one `PH-` ID per DSP that has an invited buyer, read from the catalog deal's per-DSP `dealIds` map; `dspLabel` is Google DSP (DV360) / The Trade Desk / Amazon Ads DSP), `slots` (display type, playlist · zone, IAB zone, advertiser slot n / loop slot n, plays per window), `advertisers` with their DSP (ordered DV360, The Trade Desk, Amazon DSP, then name), `fill`, `pacing` (Programmatic guaranteed only, else `null`), `revenue` (earned) and `cpm` (`kind` is `floor` for Private auction, `fixed` otherwise). An unknown `dealType` returns 400.
- The display type page filter applies to every part of a deal row: `slots` and `fill` cover only assigned slots on the filtered types, and a deal with none drops out. `fill.percent` is `null` when there is no opportunity (no cap: `fill` and Slots won are honest numbers).
- PG `pacing` is **deal-wide**: delivered is settled VAC-d (`earnedViews`) from the flight start to `dateTo`, and the store and display type filters are ignored so the guarantee and delivered cover the same scope (`scope: 'deal'`). One pass over the delivery rows, grouped by deal, serves every PG deal. It is as at `dateTo`: before the flight `startsInDays` is set and `percent` is `null`; during it `daysElapsed` / `daysRemaining` count from the flight start; after it `daysRemaining` is 0, `flightEnded` is true and `guaranteedToDate` equals the whole-flight guarantee. `guaranteedToDate` = forecast × (1 − buffer) × days elapsed / flight days.
- `GET /advertisers` — `top` (10 by revenue) and `all`: earned revenue, `share` (of earned revenue, whole numbers adding to 100), `dealsOn` (names and types), `slotsCovered`, `slotsWonPercent` (`null` with no opportunity; `slotsWonCount` / `slotsOpportunity` give the counts), `effectiveCpm` (settled billing) and `dsp`. `slotsWon.complete` is false when the range is longer than the 90-day settled-bid retention (README open question 3).
- **Decision:** slot records carry no position, so a display type's sold + unsold slots inside operating hours are split equally across its advertiser positions. Opportunities are sold + unsold + offline (matching `calc.fillPercent`). Deal `fill` = slots won on the deal ÷ the opportunities of its assigned slots; `slotsWonPercent` is the same for an advertiser's covered slots, counting only the advertiser's own wins on its deals' positions (not wins on those display types from other deals or the open auction), and only covered slots on the filtered display types.
- An advertiser login sees only the deals it is invited to, with only its own buyer and the deal ID for its own DSP, and only its own advertiser row.

## Endpoints: advertiser view
`delivery`, `deals-by-display-type`, `audience` and `my-targeting` are declared `advertiserAccess: true`. They are per advertiser: an advertiser login is pinned to its own id by `scopeFilters`; a retailer user must pass exactly one `advertiserIds` value (400 otherwise). They never return another advertiser's id, name, plays or CPM, and no downtime, offline or lost-revenue field.
- `GET /delivery?dealId=` — `totals` and `days[]` (every day in the range): `playsWon`, `spend`, `vsPreviousDay` (`change`, and whole-number `percent` unless the previous day was 0; the first day compares with the day before `dateFrom`) and `deals[]`, one block per deal in scope (the deals the advertiser buys or has delivery on) then the open auction, in that order. Private auction and Open auction blocks: `playsWon`, `allPlays` (all buyers), `sharePercent`, `yourCpm` (omitted with no plays won), `winningCpm {average, highest}` and `floorCpm {min, max}` (the deal floor, or the range of the floors of the display types its campaigns run on). Programmatic guaranteed and Preferred deal blocks: `playsWon`, `fixedCpm`, `otherBuyers: "None"`. `dealId` is a deal id or `open-auction` and narrows the lines and the blocks; an id that is not one of `dealOptions` is 400. `pacing[]` (Programmatic guaranteed only): the flight and a `series` of `guaranteed` against `delivered` VAC-d, the advertiser's own delivery cumulative from the flight start.
- **Winning CPM** is shown only when at least `MIN_OTHER_BUYERS_FOR_WINNING_CPM` (2, `src/constants.js`, README open question 4) other buyers won plays on that block that day; otherwise the field is omitted. `average` is revenue ÷ VAC-d across all winning buyers on the block that day (the advertiser included), `highest` the highest cleared CPM of any winning buyer (per store and display type). Buyers are only counted, never named. The service returns cleared CPMs as the source has them: it never clamps to the floor.
- `GET /deals-by-display-type` — `groups[]` in shopper-journey order, one per display type the advertiser's deals are assigned to or delivered on, each with the display type hover card, `dealCount`, `slots`, `playsWon`, `assumedViews`, `spend`, `effectiveCpm`, `sharePercent` (share of the advertiser's deal spend; whole numbers adding to 100) and `deals[]`: `name`, `description`, the advertiser's own DSP `dealIds`, assigned `slots`, `playsWon`, `assumedViews`, `spend`, `effectiveCpm` and `share {playsWon, allPlays, percent, advertisersOnDeal}` (a count, never names). Open auction plays are not on a deal and are not included. `slotsWon.complete` is false beyond the 90-day settled-bid retention.
- `GET /audience` — `assumedViews` (VAC-d delivered) and a daily `trend`.
- `GET /my-targeting` — `level` (omitted when no campaign is live in the range), `variablesUsed`, `scheduling {uses, scheduledCampaigns, campaigns, schedules}`, `otherVariablesAvailable {Localised, Personalised}` (Shared Targeting Variables shared with the advertiser's DSP that its campaigns do not use; `catalog.sharedVariables[dsp]`, defaulting to all Localisation and no Personalisation) and `usesEverySharedVariable`.
- **Reconciliation:** parts are rounded first and totals are their sums (money to the cent per day or per deal row, plays and views as whole numbers), so days, rows and groups add to the totals returned, and the totals equal the advertiser's billing for the same filters to within a cent per rounded part. `spend` and `effectiveCpm` use all billing (settled and not yet settled), so spend ÷ assumed views × 1,000 equals the CPM shown beside it.
- **Limit:** because totals follow the page filters, an advertiser who narrows `storeIds` could difference two responses to estimate one other buyer's plays. Closing that needs a minimum-cohort rule on the filtered views, which the decision on README open question 4 does not cover.

## QuickSight datasets and MCP tools
REQUIREMENTS §2 and §7 step 4: the same API, exposed two more ways. **No on-page CTA links to either.** Both are thin: a dataset or a tool call runs the endpoint's own handler through `runRoute` (`src/query.js`), the same function the HTTP routes use, so the role check, page filters, server-side advertiser scoping and rounding are the API's, not a copy that could drift.
- **QuickSight datasets.** `GET /datasets` lists the datasets the caller may read; `GET /dataset?name=<dataset>&format=json|csv` returns one as `{name, description, grain, columns:[{name,type}], rows}` (`type` is STRING, INTEGER, DECIMAL, DATE or BOOLEAN) or as CSV with a header row. All page filters and the endpoint's own parameters (`granularity`, `dealType`, `dealId`, ...) pass through. Rows are flat: nested objects become `a_b` columns, lists become `"; "`-joined text, and CSV cells that start with `= + - @` are neutralised. Retailer datasets: `summary`, `revenue`, `yield`, `display-types`, `slot-value`, `slot-allocation`, `missed-revenue`, `deals`, `advertisers`, `maturity-ladder`, `maturity-advertisers`, `maturity-variables`. Advertiser datasets: `delivery`, `delivery-deals`, `deals-by-display-type`, `audience`, `my-targeting` (plus `display-types`). A dataset is advertiser-readable exactly when its endpoint is; an advertiser asking for any other is 403, and its `advertiserIds` is pinned to itself. Point QuickSight at the CSV or JSON URL with a bearer token (a QuickSight data source that cannot send one needs the gateway in front of this service to add it); QuickSight needs a stable schema, so an empty range returns `columns: []`.
- **MCP tools.** `POST /insights/v1/retail-media/mcp` is a JSON-RPC 2.0 MCP endpoint (`initialize`, `ping`, `tools/list`, `tools/call`; batches accepted; 64 KB body cap). One read-only tool per endpoint (`retail_media_summary`, `retail_media_revenue`, `retail_media_yield`, `retail_media_display_types`, `retail_media_slot_value`, `retail_media_slot_allocation`, `retail_media_missed_revenue`, `retail_media_deals`, `retail_media_advertisers`, `retail_media_maturity`, `retail_media_delivery`, `retail_media_deals_by_display_type`, `retail_media_audience`, `retail_media_my_targeting`) plus `retail_media_dataset` (no name lists the datasets). Arguments are the page filters plus the endpoint's own; an unknown argument is a tool error. Results are the endpoint's JSON as `structuredContent` and as text. Same bearer-token authentication as every route (401 otherwise); `tools/list` shows an advertiser only the tools it may call, and calling any other returns an `isError` result.
- **Decision (to confirm):** MCP is a plain JSON-RPC POST endpoint rather than an SDK server, because this service has no dependencies; the "MCP plumbing" owned by PH Core (REQUIREMENTS §6) may front it or replace the transport without changing the tools.
- Tests: `test/export.test.js` (datasets equal the endpoints, CSV, advertiser isolation and spoofing, MCP protocol, tool results equal the endpoints, bad arguments).
