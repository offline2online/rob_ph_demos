# Requirements

1. **A templated web page; an MP4 is only an optional export.** It plays live in the campaign as a URL, so store data and the footer are always current, and that URL is still how a campaign plays a promotion. The Beaumaris MP4s are only the design reference. For a player that cannot run the live page, the editor's **Download MP4** (item 29) exports one promotion for one pharmacy as a file.
2. **Portrait (1080x1920, default) and landscape (1920x1080)**, set by `orientation=portrait|landscape`. Both must run in the Android 12 player.
3. **Campaign URL:** `pharmacy-screen.html?device=${UniqueDeviceID}&promo=<promo id>&orientation=<portrait|landscape>`. The PH player swaps `${UniqueDeviceID}` for the screen's own ID. **The URL never carries a store code** and is the same for every pharmacy. The editor offers a "Copy experience URL" button and, beside it, the playback duration to enter in the campaign (the promotion's length plus one second, rounded up, so the last scene finishes), with an info tooltip giving the campaign setup steps (full editor only; the pharmacy view, item 25, does not show them).
4. **Store data comes from the Location API by device:** `GET {baseUrl}/location-api/device/{UniqueDeviceID}/campaign_data` with `x-api-key`. PH resolves the device to its display and store. Without a device ID, show a safe "Invalid screen URL" state.
5. Fields used from `data`:
   - `store_location.store_code`, `store_name`, `store_timezone`
   - `store_info.opening_hours[]` (`open_day`, `open_time`, `close_day`, `close_time`, `is_active`), handling sessions that cross midnight
   - the store's **special hours** (dated exceptions set in PH: `name`, `date` "YYYY-MM-DD", `open`, `openTime` / `closeTime`), returned by the proxy as `store_info.special_hours[]` (item 16)
   - `store_info.address_info.suburb` (`${Suburb}`), `address`, `phone_number` (`${Phone}`), `state` (`${State}`)
   - store logo (transparent PNG), once the Location API returns it (PH-181)
6. **Polling and resilience:** poll store data every 20 s and the published config every 15 s (answered `304` with no body while nothing changed), and both at once when the page is shown again or the network returns; try the last good server first, then fall back through the others; one request in flight; re-render only on change; keep the last good result; show an on-screen error if every server fails.
7. **PH API token: set in Settings, stored encrypted.**
   - Settings has a "Personalisation Hub API" section: the API base URL and the API token (`x-api-key`).
   - A base URL can be saved only on a host in `PH_API_ALLOWED_HOSTS` (default: the host of `PH_API_DEFAULT_BASE_URL`; `.example.com` allows any host under it), because the token is sent to it; any other host is refused with `BASE_URL_HOST_NOT_ALLOWED`, so a stolen admin session cannot point the token at another server.
   - The token field is **write-only**. After saving, the UI shows only that a token is set and its last 4 characters, with Replace and Remove options.
   - The token is **never stored as plaintext.** Only its ciphertext is kept, in a server-only store that no client can read, using envelope encryption: the data key is wrapped by Cloud KMS in our test environment (Firestore `pharmacyScreen/private/settings/phApi`, which the rules deny to every client) and by AWS KMS or Secrets Manager inside the retailer's VPC for miPharmacy. It is decrypted only inside the proxy. Never in plain text, browser storage, a client-readable document or page source.
   - Screens never receive the token. A server-side proxy decrypts it and adds `x-api-key` to Location API calls.
   - Saving, replacing and removing the token need an admin role and are audit-logged. Supports rotation without redeploying screens.
8. **One shared module** for the Location API client (proxy call, server selection, polling).
9. **Promotions are a shared module:** name, promo ID (unique, used as `promo=`), template and, on every promotion except Seasonal and Sales Promos, a Schedule (item 10). Defaults: **Sales Promos** (`promo=sale`, listed first and the editor's first tab; a built-in: it cannot be deleted and its promo ID and template cannot be changed, `config-api/src/service.js`; item 28), Morning (`promo=morning`), Afternoon (`promo=afternoon`), Closed (`promo=closed`), Seasonal (`promo=occasions`; renamed from Occasions on 20 Nov 2026, the promo ID kept so existing campaign URLs keep working). Each pharmacy fills in its own content. Seasonal plays one of six seasons (Christmas, New Year's, Australia Day, Valentine's Day, Easter, Anzac Day) **by date, automatically**: each season has start and end dates, inclusive and the same every year (defaults: Christmas 15–27 Dec, New Year's 28 Dec–5 Jan, Australia Day 26 Jan, Valentine's Day 14 Feb, Easter Good Friday to Easter Monday worked out for each year, Anzac Day 25 Apr), and the screen plays the season whose dates hold the store's date (in `store_timezone`), moving to the next by itself at midnight with nobody changing anything. Where two overlap, the one that started most recently plays. Outside every season's dates it plays the **Fallback** (23 Nov 2026): the pharmacy's brand colour, "Thank you, ${Suburb}" / "for supporting your local pharmacy", its logo and name; exactly 7 s, three beats (2 + 3 + 2). A season takes over on its start date and the Fallback returns the day after its end date, so the slot is never empty. **Activate on display** (item 25) is a one-off: what it puts on a pharmacy's screens plays until that season's scheduled end date (the Fallback during a season: until that season would have ended), then the Fallback, and is not carried into next year (`content.activation`, `docs/DATA-CONTRACT.md`). Each season's start and end dates are changed in the editor (Dates card, headed "Every year: <start> to <end>"; Easter shows this year's Good Friday to Easter Monday), in the full editor and in the pharmacy view (item 25); edited dates are that pharmacy's schedule from then on, every year. **Seasonal is each pharmacy's own**: its Activate on display and every season's copy, dates and timings are saved with that pharmacy's content and change only its screens; they are never inherited live from the master template (item 23).
10. **Scheduling is done in Personalisation Hub Core**, which decides when a campaign plays; the screen plays whatever promotion `promo=` names. Every promotion except Seasonal and Sales Promos has a **Schedule**, set by an administrator in the full editor (New promotion, or under the promotion's promo ID and template): **No schedule** (the default; nothing is stored) or **Annual**, a start and an end date (month and day, inclusive) that repeat every year (switching to Annual starts with today to 31 Dec). The dates are saved on the promotion and published in its screen config as `schedule` (`{ "type": "annual", "from": "MM-DD", "to": "MM-DD" }`, present only for an annual schedule; `docs/DATA-CONTRACT.md`) for Personalisation Hub Core's scheduling. Seasonal has no Schedule: it picks its season by date (item 9). Sales Promos has no Schedule either (it has no promotion settings section): it runs until its end date (item 28). The pharmacy view does not show Schedule (item 25).
11. **Templates are a reusable library.** Built-ins "Promotion scenes", "Opening hours", **"Sales promo"** (`builtin-sale`, kind `sale`, `config-api/src/builtins.js`; reserved for the Sales Promos promotion and drawn from each pharmacy's sale copy, item 28, so it has no editable HTML), the six seasonal templates (one per season, themed, neutral and inclusive; Anzac Day commemorative, fades only) and the **Fallback** template ("Thank you", the pharmacy's brand colours, logo and name; item 9) are read-only and cannot be cloned. What plays on Seasonal is decided by the dates and **Activate on display** (items 9, 25); the **Currently active promotion** drop-down only picks which of these templates the editor previews and edits. Each seasonal template is a standalone, full-screen design (the designs approved on 20 Nov 2026) in both orientations, with no brand panel, logo, brand colours, icon tiles, "Open today" bar or holiday line. Its copy plays as beats, by default on a 12 s loop (Christmas 2 beats, the others 3; each beat a main line and, where the design has one, a small label line), so the campaign's playback duration is 13 s at the defaults. Each beat's seconds on screen can be edited (1-60 s); the loop is then their sum and the editor's playback duration follows. Its fonts and the Christmas photo (Unsplash, credited in `pharmacy-screen/README.md`) are self-hosted with the screen, so no screen calls out for them. Users can clone, name and edit HTML (with `${…}` tokens), CSS and portrait/landscape backgrounds, and reuse templates across promotions. A pharmacy can give any token its templates use a value of its own (item 24).
12. Promotion scenes: greeting, service chips, one scene per slot (icon, headline, accent line, line 1, line 2), then a "Walk in today" close. Slots can be added (from the service library or blank), deleted and reordered; each scene has its own duration.
13. **Service library:** 28 ready-made slots researched from the five launch pharmacies, all listed in the Add promotion picker for every pharmacy (searchable, grouped by category; no per-pharmacy filter, because pharmacies' service lists may be out of date). Centrally maintained in the build. Copy needs TGA advertising review before go-live.
14. Opening hours: rotating headlines, each with its own seconds on screen (1-60 s; default 2.7, 2.7, 2.6), full weekly hours, holiday note and phone. The hours card's badge shows the store's state at the time on screen (27 Nov 2026): **OPEN NOW** while open, **CLOSING SOON** in the last 30 minutes, **CLOSED NOW** before opening and after closing, worked out in `store_timezone` like the Open today bar (special hours included) and updated on the minute. A `store_timezone` that is not an IANA zone (`AEST`, a Windows zone name, a city list, a UTC offset) is read as the Australian zone it names, and an empty or unrecognisable one as `Australia/Melbourne` (Sydney and Melbourne keep the same time), never the player's own clock.
15. **Editable "Open today" bar** per promotion (not on Seasonal, which has no bar, nor on Sales Promos, whose footer band shows the sale, item 28): messages for open, last 30 minutes, before opening and after closing, using `${CloseTime}` and `${OpenTime}`, worked out in `store_timezone`. Can be hidden.
16. **Public holidays and special hours:** a store's special hours from Personalisation Hub are used wherever the screen works out whether it is open, in the store's time zone: the "Open today" bar and its `${OpenTime}` / `${CloseTime}` on every template. A special date marked closed is closed all day; one with times replaces that weekday's weekly hours (even when they are the same); two entries on one date are two sessions; a session crossing midnight behaves like a weekly one, and a weekly session running into a special date stops at midnight. The opening hours template (Closed) lists the nearest upcoming special dates (from today, at most 6, no more than 90 days ahead; a passed date never) under the weekly hours as "Special hours", each with its date ("Thu 24 Dec"), PH's name for the day ("Christmas Eve"; none: the date alone) and its times or Closed. While any are listed they replace the "Public Holidays: Please call to confirm" note, and the template's default third headline saying the same is left out (edited headlines are kept); the card shrinks to fit (`js/fit-text.js` `fitCard`). With none, the note shows "Public Holidays: Please call to confirm" exactly as before (Seasonal has no holiday line). Personalisation Hub still decides when Closed or a seasonal promotion plays.
17. **Tokens in copy use the PH format** `${TokenName}`. `${Suburb}` uses only the suburb and is left blank (with its leading comma or line break removed) if there isn't one. `${StoreName}` is the Location API store name, else the pharmacy's name (Christmas and New Year's sign off with it; the other seasons use `${Suburb}` only). `${CloseTime}` and `${OpenTime}` are today's times, always worked out live. `${Phone}`, `${State}` and `${StoreCode}` come from the store's data (`store_info.address_info.phone_number`, `store_info.address_info.state` and `store_location.store_code`). Every copy field (scene and opening-hours headlines, Open today bar messages, accent lines, Line 1 / Line 2, service chip labels, and the seasonal Small line above, Main line and Line below) has **+ Add token** on its label row, in the full editor and the pharmacy view: a menu of Store name, Suburb, Store code, State and Phone number that inserts the token at the cursor (`ADD_TOKENS` in `pharmacy-screen/js/tokens.js`; `rt()` / `pt()` in `pharmacy-screen/admin/js/rich-text.js`). Under each copy field, the `${…}` tokens it uses are shown as chips, updated as you type and hidden when it uses none. Brand name, Website, Languages spoken by store staff and Localised copy are not offered, but `${BrandName}`, `${Website}`, `${LanguagesSpoken}` and `${LocalisedCopy}` still fill where copy already uses them. These have no store data: each shows only a value set in Settings → Tokens, and nothing until one is set. `${StoreName}`, `${CloseTime}` and `${OpenTime}` cannot be set by hand; any other token can be given a value by hand per pharmacy, which wins over the store's data (item 24).
18. **Copy must never leave the brand panel.** Headlines and accent lines shrink automatically to stay inside the triangle (portrait) or arrow (landscape). Seasonal has no brand panel: each beat's copy shrinks to stay inside the design's own text box.
19. **Animations match the Beaumaris videos:** content fades out at scene end, except the promotion's last scene on a screen, which stays (no fade out; Seasonal: the last beat stays visible), item 27; headline fades in; icon tiles pop in one after another with labels after; copy fades up; icons gently float (outer and middle tiles in opposite phase). Off when reduced motion is set (on Seasonal the decorations stand still and the beats still change).
20. Branding per pharmacy: logo and primary/accent colours; icon tiles use a brighter version of the primary. Seasonal uses none of these: each season keeps its own design's colours, with no logo or icon tiles.
21. Adding a new pharmacy needs only its device registration in PH and its branding and content config.
22. **Handover package is part of done.** The repo and the Google Shared Drive release must include: deployment guide, configuration reference with `.env.example`, data contract, `README.md`, `AGENTS.md`/`CLAUDE.md` for deployment agents, test checklist, admin user guide, mock data, and a `START-HERE.md`, all kept in sync with the code. The build is tested in our environment first, then shared with the miPharmacy team to deploy into their own environment and connect to their own Personalisation Hub instance.
23. **Master template.** Each promotion has a master template: the default content (greeting, promotion slots, walk-in close, Open today bar, opening-hours headlines and address) that every pharmacy, including each new one, inherits section by section. Branding (name, logo, colours) is always the pharmacy's own. Seasonal content is never inherited live: the master's seasonal copy, dates, timings and season are only what a new pharmacy starts with and what a pharmacy's **Copy from master** (two clicks) copies for the season on screen, so a change to the master reaches no live store; the seasonal section on a pharmacy reads "This pharmacy's own" (`config-api/src/seasonal.js`). In the editor (Promo preview → Master template) the master is edited like a pharmacy's content. Its preview uses the default colours and, having no store of its own, shows `${Suburb}`, `${StoreName}` and `${Phone}` exactly as written ("Good morning, ${Suburb}", "Phone ${Phone}"), with `${CloseTime}` / `${OpenTime}` showing the sample hours' times; a pharmacy's preview fills them in with that pharmacy's data. This is the preview only: nothing is saved and the master's copy keeps its tokens. On a pharmacy each section shows "Inherited from master" or "Managed separately", with "Edit for this pharmacy" (a message confirms the master no longer reaches that section) and "Revert to master". The launch master is Beaumaris Pharmacy's content. Sales Promos copy belongs to no master section: a pharmacy's own sale copy, once saved, always wins, and the promotion's master (seeded: the Big Brand Sale) supplies the copy of a pharmacy that has none (item 28).
24. **Tokens set by hand, per pharmacy (Settings → Tokens).** Settings lists every `${…}` token the pharmacy's promotions and templates use, in copy and template HTML (the master template's inherited sections included), with the promotions that use each. `${StoreName}` is not listed: it is live (item 17), falling back to the Pharmacy name, whose label in Pharmacy details shows the token. `${CloseTime}` and `${OpenTime}` are not listed either: they change through the day, so they are never shown as fixed values. A value typed there shows on that pharmacy's screens instead of the store's data for `${Suburb}`, `${Phone}`, `${State}` and `${StoreCode}` (e.g. when Personalisation Hub has the wrong suburb), and instead of nothing for any other token a custom template or copy uses (e.g. `${BrandName}`, `${Website}`, `${LanguagesSpoken}` or `${LocalisedCopy}`, item 17); clearing it goes back to the store's data. Template layout slots (`${Headline}`, `${Logo}`, `${Content}` and the like) cannot be set, and a value stored earlier for `${StoreName}`, `${CloseTime}` or `${OpenTime}` is ignored on screens and dropped the next time the pharmacy is saved. Values are plain text, at most 200 characters and 50 per pharmacy, saved as you type and shown in the preview. Stored as the pharmacy's `tokens` and published with its screen config (`docs/DATA-CONTRACT.md` → "3. Template tokens").
25. **Pharmacy view.** `admin/?store=<store code>` (or `storeCode`) opens the editor locked to that pharmacy, titled "Display Promotions" and showing only its promotions and the live preview: no Promo preview drop-down and no Settings (its details, tokens and branding, the other pharmacies and the PH API settings are set in the full editor), no "Use ${Suburb} in any line…" hint, no "Remote config for this pharmacy", and no Copy experience URL or playback duration (with its tooltip) under the preview (the campaign is set up in the full editor). Its own content is editable: an inherited section's **Edit** makes it its own, and promotion slots can be added from the service library or blank, reordered and deleted, with at most 3 slots per promotion (Add promotion is hidden at 3). Scene timings are set by an administrator only, so no seconds-on-screen control shows. **Restore to default**, at the top of the page in place of "shared by all pharmacies", puts every section of every promotion back to the master template (two clicks), except Seasonal and Sales Promos, which it leaves alone. On **Sales Promos** the pharmacy edits its own sale copy (item 28: headline, brands, offer, caption, end date, panel label and footer; not the scene seconds). The shared promotion settings (promotion name, promo ID, template, **Edit HTML** and the `promo=` line) are not shown on Sales Promos, Morning, Afternoon, Closed or any other non-seasonal promotion (they are shared by every pharmacy and only an administrator changes them, in the full editor), except that on Seasonal only the **Currently active promotion** drop-down and **Activate on display** show (no promotion name, promo ID or `promo=` line). Seasonal is the pharmacy's own (item 9): the **Currently active promotion** drop-down opens on what this pharmacy's screens play today, marked "· on display", and picking another only previews and edits it; **Activate on display** puts the one picked on this pharmacy's screens now, the one-off in item 9 (its tooltip gives the end date), and reads "On display" when it is already playing (not on the master template); the season's Dates card (headed "Every year: <start> to <end>"; Easter: this year's Good Friday to Easter Monday) has Starts / Ends pickers that save this pharmacy's dates, and **Copy from master** (two clicks) replaces the copy and dates of the season on screen with the master's as they are now. Changing them changes only this pharmacy's screens. The master template and other pharmacies are hidden. A Retail Admin session from Personalisation Hub opens this view as a store user for their own store, without the admin role (item 26): this is enforced on the server (`config-api/src/api.js` routes marked `store`, `src/service.js`), and a store code in the URL that is not theirs shows "Access denied". An administrator can open it for any pharmacy.
26. **Sign-in from Personalisation Hub, two roles.** On our Firebase environment the editor has no sign-in of its own: it runs inside Personalisation Hub, in HQ Admin (Pharmacy Promos) and Retail Admin (Display Promotions), and uses the PH session of the person looking at it. The PH page hands the session token to the editor's frame by `postMessage` (only when the editor asks, only to the editor's own origin, never in the URL); the server checks it with PH (`POST /api/auth/ph-session`) and issues a short editor session carrying the role and stores, checked again with PH at least every hour. An HQ Admin session with role `ADMIN` is an **administrator**: everything. A Retail Admin session for a store with a store code is a **store user** for that one store: the pharmacy view only (item 25). Anything else, no session, or the editor opened outside PH shows "Access denied". Roles are enforced on the server, and the editor can be framed only by PH (`frame-ancestors`). `PS_ADMIN_AUTH` at deploy time chooses `ph`, `ph+firebase` (the changeover default) or `firebase`. The Firebase sign-in (admin role) is the fallback while `PS_ADMIN_AUTH=ph+firebase`. The AWS deployment keeps its OIDC sign-in. Contract: `docs/PH-EMBED.md`; settings: `docs/CONFIGURATION.md` → `PS_ADMIN_AUTH`, `PS_REQUIRE_PH_SESSION`.
27. **Playback on a screen: once through, then hold the last scene.** On a player a promotion plays inside a rotation of campaigns, so it plays once through and then stays on its last scene (Seasonal: its last beat), fully drawn, with no leaving fade and no return to the first scene, until the player moves to its next campaign. The held scene still follows the store's clock (the Open today bar, "Closed now") and new data, redrawn in place without restarting playback; on Seasonal the decorations keep moving. Playback starts from the first scene again when the page is loaded again, when it is shown again after being hidden (`visibilitychange`, or `pageshow` from the back-forward cache), and when the season changes at midnight. `loop=1` in the campaign URL keeps the earlier behaviour, looping forever, for a screen that shows this one campaign only. The editor's preview always loops, and `scene=<n>` (testing) still holds one scene. Spec: `pharmacy-screen/README.md` → Playback; `docs/CONFIGURATION.md` → Fixed behaviour "Playback (screen)" and Query parameters `loop` (`pharmacy-screen/js/player.js`).
28. **Sales Promos (`promo=sale`, 26 Nov 2026).** The first default promotion (item 9) plays the built-in **Sales promo** template (item 11; `renderSale()` in `pharmacy-screen/js/render.js`): two scenes on the brand shell in the pharmacy's own colours and logo, a 10 s loop at the defaults (playback duration 11 s), portrait and landscape: **the brands** (headline in the brand panel, 1-6 brand cards popping in, a caption; 3.5 s) and, after a 0.65 s transition in which the brand colour fills the screen, **the offer** (rays, "UP TO", the value counting up from 0, "OFF", the pulsing "SALE FINISHES" panel, the brand list; 5.85 s). The footer band shows the sale. Its copy is **each pharmacy's own** (administrators edit any pharmacy's, a store user their own in the pharmacy view, item 25), stored as `content[<promotion id>].sale` and checked by the config API (`config-api/src/validate.js`, a bad value is refused with 400; `docs/DATA-CONTRACT.md`): headline line 1 and line 2; **Brands**, 1 to 6 (added, removed and reordered; at most 30 characters each); the offer lead-in ("UP TO"), **value** (a whole number 1-99, shown with %) and suffix ("OFF"); caption line 1; the **end date**, chosen with a date picker, whose wording with the weekday ("Wednesday 2nd December") is generated from the date, never typed, and feeds caption line 2, the panel and the footer; the panel label ("SALE FINISHES"); each scene's seconds on screen (1-60 s, administrators only); and the footer band's two lines, derived from the headline, offer and end date unless **Write my own** is ticked for custom text. A pharmacy with no sale copy plays the promotion's master (the Big Brand Sale). **The end date is wording only** (caption line 2, the panel and the footer): `promo=sale` always plays the Sales promo template, whatever its end date, and Personalisation Hub schedules when it plays. When the chosen date has passed, the editor shows one small hint under the date field, "This date has passed. The screen still plays whenever Personalisation Hub schedules it." (no chip, no alert; `admin/js/editor.js`). Spec: `pharmacy-screen/README.md` → Sales Promos; `docs/USER-GUIDE.md` → Sales Promos.
29. **Download MP4 (Android 12 signage format, 26 Nov 2026).** Under the editor's preview, beside Play/Pause and the opening hours pill, **Download MP4** makes an MP4 of the promotion on the preview for the selected pharmacy (its own store data from Personalisation Hub, read with the pharmacy's **Screen device ID**, Settings → Pharmacy details; never the sample hours) and orientation (1080x1920 portrait, 1920x1080 landscape): one full loop from the first scene, stepped frame by frame at 25 fps from the real screen page (`pharmacy-screen.html?capture=1`) in headless Chromium and encoded by ffmpeg on the server, in the format recorded in `README.md` → "Download MP4 (Android 12 signage format)" (H.264 Main 4.0, yuv420p, 25 fps CFR, timescale 12800, GOP 50 with no scene-cut keyframes, up to 3 B-frames, no audio track, BT.709 limited range, CRF 18 capped at 6 Mbit/s, no SEI, `mp42`, faststart, no metadata). The button is disabled with a tooltip until a pharmacy with a Screen device ID is selected; edits are saved first (a failed save refuses the download); it shows "Preparing video…" with progress and cannot be clicked twice; a failure shows a plain message and the button is usable again. Administrators only (`POST /api/admin/videos`, `GET /api/admin/videos/{id}`), one render at a time per deployment (a second gets 429 "A video is already being made"), loops up to 120 s, and the file downloads from a link that expires after an hour; exported files are deleted after a day. File name `<pharmacy>-<promotion>-<portrait|landscape>-<seconds>s_android.mp4`, lower case and hyphenated. Works on both deployments (Firebase: a Cloud Tasks function; AWS: a Lambda worker). When a promotion plays stays with Personalisation Hub (item 10).
30. **Screen device ID fills in the pharmacy and gives the preview live data (26 Nov 2026).** In Settings → Pharmacy details the **Screen device ID** is the first field, full width, with the help line "Paste the Personalisation Hub device ID of one of this pharmacy's screens. Its store details are then read live from Personalisation Hub." When an ID is entered (on paste, or Enter / leaving the field after typing; **Check** reads it again) the editor reads the device's store data through the PH API proxy (`GET /api/device/{id}/campaign_data`, the screen's own route and cache) and shows under the field the store name, store code, address (address, suburb, state, postcode), phone, timezone, today's opening hours and the logo Personalisation Hub returns, marked "Live from Personalisation Hub" with the time it was read. An empty pharmacy name and store code are filled in from it (`store_location.store_name`, `store_location.store_code`) and listed as filled in; the pharmacy is created or saved by the normal autosave. Nothing a person typed is overwritten (superseded by item 31: a verified device's values now replace typed ones and their inputs leave Settings): a different name, or a `${Suburb}` set by hand (Settings → Tokens) that differs from `store_info.address_info.suburb`, shows Personalisation Hub's value beside it with **Use Personalisation Hub's** (for the suburb this clears the hand-set value, so screens show Personalisation Hub's suburb live). The suburb, logo and opening hours are never copied into the pharmacy record: a blank `${Suburb}` already shows the store's suburb, screens already prefer Personalisation Hub's `logo_url` over the uploaded logo (the uploaded logo stays as the fallback), and hours are always read live so they cannot go stale. The ID is saved only once Personalisation Hub confirms its store is this pharmacy's: a device of another store is refused ("This device belongs to <store name> (<code>), not this pharmacy.", and for a new pharmacy, a store already set up here is named), and nothing is saved for a malformed ID, an ID Personalisation Hub does not know, or while Personalisation Hub cannot be reached or its API is not set up (each with its own plain message under the field; an ID waiting to be checked has **Check again**). When a saved ID's store cannot be read, the last read is kept and the message says when it was read. Clearing the field removes the ID. A pharmacy without one shows a non-blocking prompt in its details ("No screen device ID yet. Until one is added, the preview shows sample data and Download MP4 is off.") and "· no screen device ID" after its name in the pharmacy lists; **Add pharmacy** starts with the device ID field, so a pharmacy can be set up from its device ID alone. **Every preview** of a pharmacy with a device ID (Sales Promos, Morning, Afternoon, Closed, Seasonal and its seasons, portrait and landscape; the pharmacy view too) is drawn with that store's live data through the screen's own store mapping (`storeModel()` in `js/render.js`): its opening hours, including the Open today bar and the Closed promotion's next opening, suburb, store name and logo, as its screens show them. The pill under the preview then reads **Live opening hours** (tooltip: read from Personalisation Hub for <store name>, at <time>); with no device ID, or when nothing could be read, it stays **Sample opening hours** and its tooltip says how to get live data. The data is read when the pharmacy is picked and on Check; nothing polls. The master template keeps sample data. Scheduling, the public screen, its campaign URL and the published config are unchanged (the device ID is never published). Spec: `pharmacy-screen/admin/README.md` → Settings, Live preview; `docs/USER-GUIDE.md` → Settings.
31. **Values from Personalisation Hub are not editable once the Screen device ID is verified (27 Nov 2026).** Once a pharmacy's Screen device ID is verified (item 30: the lookup through `/api/device/{id}/campaign_data` succeeds and the store is this pharmacy's), every value Personalisation Hub returns for it is managed there. Covered, each only when Personalisation Hub returns a value for it: the **pharmacy name** (`store_location.store_name`), the **store code** and the `${StoreCode}` token (`store_location.store_code`), the `${Suburb}`, `${State}` and `${Phone}` tokens (`store_info.address_info.suburb`, `.state`, `.phone_number`) and the **logo** upload (`store_info.logo_url`). On verifying, the pharmacy takes Personalisation Hub's name and store code, a value set by hand for any of those tokens is dropped, and Settings, the add-pharmacy flow and the Tokens editor no longer show an input for them; Personalisation Hub's values show instead as one line of plain read-only text under the device ID (e.g. "Beaumaris Pharmacy · VIC-MP-001 · Beaumaris 3193": name · store code · suburb and postcode), with the full read-only store details below it, each marked with the token it fills. **Per field**: a value Personalisation Hub has none for (`logo_url` null for Beaumaris today, or no phone) keeps its input, so the screen is never left blank. `store_timezone`, `opening_hours`, `special_hours`, the address and postcode have no input in the admin (they are read live), so nothing changes for them. **Stay editable** (no source in the API): the Primary and Accent colours, any other token (`${BrandName}`, `${Website}`, `${LanguagesSpoken}`, `${LocalisedCopy}` and any custom one), every promotion's copy, and the device ID itself. Templates, previews and screens show Personalisation Hub's values for these tokens (a dropped hand-set value cannot override them). **The config API enforces it**: the pharmacy record keeps, with its `device`, the list of values Personalisation Hub supplies (`phFields`, sent by the editor with the verified device; `config-api/src/validate.js` `lockPhFields`). On a pharmacy with a device and `phFields`, a save with another name, store code or hand-set value for one of those tokens keeps the stored values (answered 200 with the record, not refused), a logo upload is refused (409) when the logo is Personalisation Hub's, and `phFields` cannot be shrunk without changing or clearing the device. A pharmacy whose device was verified before this rule takes its `phFields` the next time the editor opens it. **Clearing the device ID** (or never verifying one: no ID, an unknown ID, Personalisation Hub not reachable) leaves every input shown and editable as before, so a pharmacy without a device can still be set up. Known limit: `phFields` is set when the device is verified; if Personalisation Hub later starts or stops returning a value, clear and re-enter the device ID to update it. Spec: `pharmacy-screen/admin/README.md` → Settings; `docs/DATA-CONTRACT.md` → §4.
32. **Landscape (in-store) wording for the promotion scenes (28 Nov 2026).** Landscape screens are inside the pharmacy (above or near the dispensary), portrait ones outside it. A promotion-scenes promotion's copy can differ by orientation: sparse landscape overrides beside the copy they replace (`content.landscape` for the intro lines, `slots[i].landscape` and `close.landscape` for headline, accent line, line 1 and line 2), each falling back to the shared copy when empty, played only in landscape (screen, editor preview, Download MP4, copy-fit audit). They inherit and detach with their master section (greeting, slots, close). The editor's Portrait/Landscape tabs choose which wording the copy fields show and edit; empty landscape fields show the portrait wording as a placeholder. Defaults, seed data and fixtures carry the in-store wording for Morning and Afternoon (intro "Our services" / "Speak to your pharmacist"; close "Speak to your pharmacist" / "We're here to help" / "Ask us about any of these services", its last line unchanged; service lines such as "Pop in this morning" → "Ask us this morning"), and the library's come-in lines have landscape wording; the seed adds it to seeded content and services whose copy is still the fixture's, never changing portrait copy. Portrait wording, the greeting, Sales Promos, Seasonal and Closed are unchanged. Spec: `docs/DATA-CONTRACT.md` → §4; `docs/USER-GUIDE.md` → Promotion scenes.
